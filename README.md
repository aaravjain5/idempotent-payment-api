# Idempotent Payment API

A backend service that simulates how real payment systems (like Razorpay, Stripe, or PayPal) prevent duplicate charges when a request is retried due to network failures, timeouts, or accidental double-clicks.

Built with **Java 21**, **Spring Boot 4**, and **H2** as part of my project.

---

## The Problem

Imagine a user clicks "Pay ₹799," the payment succeeds on the server, but the network drops before the response reaches the client. The user sees a loading spinner, gets impatient, and clicks "Pay" again — and now they've been charged twice for one purchase.

This is one of the most common and costly bugs in payment systems, and it's exactly why every real-world payment API (Stripe, Razorpay, PayPal) requires clients to send an **Idempotency Key** with every request.

## How This API Solves It

Each payment request includes a unique `Idempotency-Key` header, generated by the client before the request is sent.

- If the server has **never seen this key before**, it reserves the key immediately, processes the payment, and stores the response against it.
- If the server **has already seen this key**, it skips processing entirely and returns the exact same response as before — no duplicate payment is created, no matter how many times the request is retried.
- If **two requests with the same key arrive at nearly the same instant**, only one of them is allowed to process the payment. The other detects that the key is already reserved and waits for the first request's result instead of creating a second payment.

This makes retries — and even accidental double-clicks — completely safe from the client's side.

## API Endpoints

### Create a Payment

```
POST /api/payments
Content-Type: application/json
Idempotency-Key: 7f3a9c2e-1b4d-4e8a-9f21-abc123456789

{
  "orderId": "order_101",
  "amount": 799.0,
  "currency": "INR"
}
```

**Response — 200 OK**
```json
{
  "id": "generated-payment-id",
  "orderId": "order_101",
  "amount": 799.0,
  "currency": "INR",
  "status": "SUCCESS",
  "createdAt": "2026-08-30T14:55:40.391"
}
```

If this exact request is sent again with the **same** `Idempotency-Key`, the API returns the **same response** above — and no new payment is created in the database.

### Get a Payment by ID

```
GET /api/payments/{id}
```

**Response — 200 OK**
```json
{
  "id": "generated-payment-id",
  "orderId": "order_101",
  "amount": 799.0,
  "currency": "INR",
  "status": "SUCCESS",
  "createdAt": "2026-08-30T14:55:40.391"
}
```

**Response — 404 Not Found** (if the ID doesn't exist)
```json
{
  "timestamp": "2026-08-30T15:20:00.000",
  "status": 404,
  "error": "Payment Not Found",
  "message": "No payment found with id: fake-id-12345"
}
```

### Rate Limiting

Every endpoint is protected by a simple in-memory rate limiter: **20 requests per minute per IP address**. Exceeding this returns:

**Response — 429 Too Many Requests**
```json
{
  "error": "Too many requests. Please try again later."
}
```

## Design Decisions

**Why store the response, not just the key?**
Storing only "this key was used" isn't enough — if the client retries, it still needs the *original* response back (same payment ID, same data), not just a generic "already processed" message. So the full JSON response is cached against the key and replayed on retry.

**Handling concurrent duplicate requests**
The idempotency key is reserved in the database *before* any payment processing begins, and the key column is the table's primary key. If two requests with the same key race each other, the database itself only allows one insert to succeed — the losing request detects the conflict and polls briefly for the winning request's result instead of creating a second payment. This closes the race-condition gap that existed in an earlier version of this project, where the key was only saved *after* processing — leaving a small window where two simultaneous requests could each create their own payment.

**Why a separate database for tests**
Tests initially shared the same file-based database as local development, which caused a subtle bug: rerunning the tests against a database that already contained data from a previous run made a "new" idempotency key look like a duplicate, and a test failed for the wrong reason. Tests now run against an isolated in-memory H2 database that's created fresh and destroyed after every run, so results are consistent no matter how many times or in what order the tests are executed.

**Global error handling**
Rather than letting unhandled exceptions bubble up as Spring's default HTML error page, a global exception handler converts them into consistent JSON responses — a "not found" payment, a failed validation, or any unexpected error all return a clean, predictable structure.

## Running Locally

```bash
git clone https://github.com/aaravjain5/idempotent-payment-api.git
cd idempotent-payment-api
./mvnw spring-boot:run
```

The API will start on `http://localhost:8080`. The H2 console is available at `http://localhost:8080/h2-console` (JDBC URL: `jdbc:h2:file:./data/paymentdb`, username: `sa`, no password).

## Running Tests

```bash
./mvnw test
```

Tests run against a separate in-memory database and include:
- A duplicate request with the same idempotency key creates only **one** payment
- Requests with different idempotency keys are treated independently and create separate payments
