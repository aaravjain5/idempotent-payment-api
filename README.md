# Idempotent Payment API

A backend service that simulates how real payment systems (like PayPal, Stripe or Razorpay) prevent duplicate charges when a request is retried due to network failures, timeouts, or accidental double-clicks.

Built with **Java 21**, **Spring Boot 4**, and **H2** as part of my backend project.

---

## The Problem

Imagine a user clicks "Pay ₹899," the payment succeeds on the server, but the network drops before the response reaches the client. The user sees a loading spinner, gets impatient, and clicks "Pay" again — and now they've been charged twice for one purchase.

This is one of the most common and costly bugs in payment systems, and it's exactly why every real-world payment API (PayPal, Stripe, Razorpay) requires clients to send an **Idempotency Key** with every request.

## How This API Solves It

Each payment request includes a unique `Idempotency-Key` header, generated by the client before the request is sent.

- If the server has **never seen this key before**, it processes the payment normally and stores the response against that key.
- If the server **has already seen this key**, it skips processing entirely and returns the exact same response as before — no duplicate payment is created, no matter how many times the request is retried.

This makes retries completely safe from the client's side.

## API Usage

### Create a Payment

```
POST /api/payments
Content-Type: application/json
Idempotency-Key: 7f3a9c2e-1b4d-4e8a-9f21-abc123456789

{
  "orderId": "order_101",
  "amount": 899.0,
  "currency": "INR"
}
```

**Response — 200 OK**
```json
{
  "id": "generated-payment-id",
  "orderId": "order_101",
  "amount": 899.0,
  "currency": "INR",
  "status": "SUCCESS",
  "createdAt": "2026-08-30T14:55:40.391"
}
```

If this exact request is sent again with the **same** `Idempotency-Key`, the API returns the **same response** above — and no new payment is created in the database.

---

## Design Decisions

**Why store the response, not just the key?**
Storing only "this key was used" isn't enough — if the client retries, it still needs the *original* response back (same payment ID, same data), not just a generic "already processed" message. So the full JSON response is cached against the key and replayed on retry.

**Handling concurrent duplicate requests**
If two requests with the same idempotency key arrive at nearly the same instant (e.g., a rapid double-click), there's a brief window where both could pass the "have I seen this key?" check before either has saved it. To guard against this, the idempotency key is the primary key in its database table, so the database itself rejects a second simultaneous insert. If that happens, the API catches the conflict and returns the winning request's cached response instead of failing.

**Known limitation:** in that exact race scenario, it's possible for two `Payment` records to be created even though only one idempotency key record is saved. A production-grade fix would wrap the check-then-save flow in a database transaction with a row lock. Documenting this trade-off here rather than over-engineering a student project felt like the right call — but it's the natural next improvement.

## Running Locally

```bash
git clone https://github.com/aaravjain5/idempotent-payment-api.git
cd idempotent-payment-api
./mvnw spring-boot:run
```

The API will start on `http://localhost:8080`. The H2 console is available at `http://localhost:8080/h2-console` (JDBC URL: `jdbc:h2:file:./data/paymentdb`, username: `sa`, no password).

## Running Tests

```bash
./mvnw test
```

Includes integration tests verifying:
- A duplicate request with the same idempotency key creates only **one** payment
- Requests with different idempotency keys are treated independently and create separate payments
